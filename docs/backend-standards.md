# Backend standards

The engineering bar every backend meets, whatever its architecture or language. The build
plans in [monolith/](monolith/), [hybrid/](hybrid/) and [microservices/](microservices/) refer
here instead of repeating it. Each section ends with what "done" looks like.

These are the practices a production team would expect. Each one is something to build and
understand, not boilerplate to copy.

## 1. Definition of done for an operation

An operation in `api/openapi.yaml` moves from `OFFLINE` to `LIVE` only when all of these hold:

- [ ] The request is validated against the contract; invalid input returns `422`
      problem+json with `errors[]` per field.
- [ ] Every response status and body the contract lists is produced, and nothing it doesn't.
- [ ] Auth, visibility and block rules apply (see §6). A resource the caller may not see
      returns `404`, the same as one that doesn't exist, so its existence isn't leaked.
- [ ] Creates honour `Idempotency-Key`; edits honour `If-Match` and return `ETag`.
- [ ] Lists use cursor pagination with a stable order and a `limit` cap.
- [ ] Unit tests cover the domain rules; an HTTP test covers the happy path and the main
      errors.
- [ ] `pnpm test:contract <backend> <operationId>` passes.
- [ ] Logs for the request carry the trace id, and the request appears in traces.
- [ ] The frontend works against it with **Settings → Only call endpoints marked LIVE** on.

Then flip `x-status` in the same commit (see [CONTRIBUTING.md](../CONTRIBUTING.md)).

## 2. Configuration (12-factor)

- All config comes from environment variables, validated once at startup. A missing or
  invalid value stops the process with a clear message. It never fails later at first use.
- Each backend keeps a committed `.env.example` listing every variable with a safe local
  default. `.env` stays uncommitted.
- Secrets (JWT keys, database passwords, the upload token secret) are never logged, and never
  get defaults outside local development.
- The same build artifact runs in every environment; only the environment changes.

**Done:** starting with a missing variable fails fast and names the variable.

## 3. HTTP conventions

These are already fixed by the contract; the backend's job is to honour them consistently.

| Concern | Rule |
|---|---|
| Base path | `/v1` |
| IDs | ULIDs, generated by the backend (ADR-0005) |
| Timestamps | RFC 3339, UTC, millisecond precision |
| Errors | RFC 9457 `application/problem+json` with `type`, `title`, `status`, `detail`, `traceId`, plus `errors[]` for validation (`422`) |
| Status codes | The contract's shared responses: `401` no or bad token, `403` allowed to see but not to do, `404` missing *or hidden*, `409` conflict with current state, `412` stale `If-Match`, `413` file too large, `422` validation, `429` rate limited |
| Pagination | `?cursor=&limit=` → `{ data, page: { nextCursor, hasMore } }`. Cursors are opaque (base64url of the keyset) and validated on the way in |
| Idempotency | `Idempotency-Key` on creates: store the key and user with a hash of the request and the response for 24 h. The same key with the same body replays the response; the same key with a different body returns `409` |
| Concurrency | `ETag` on editable resources (a version number or hash); `If-Match` on `PATCH`. A mismatch returns `412` |
| CORS | Allow `http://localhost:5173`. Expose `ETag`, `Retry-After`. Allow the `Authorization`, `Idempotency-Key` and `If-Match` headers |
| Rate limits | `429` with `Retry-After` |

Map every error to a problem type in one place, the error handler. Unknown errors become a
generic `500` without internals (no stack traces or SQL in responses); the details go to the
logs with the trace id.

**Done:** `grep` finds no handler that builds an error response by hand.

## 4. Data

- **Migrations** are versioned files, committed, applied by a separate command (not at app
  start in production). They are forward-only: to undo, write a new migration.
- **Expand / contract** for breaking schema changes: add the new column, backfill, switch
  reads, then drop the old one in a later migration.
- **Constraints in the database:** foreign keys, `NOT NULL`, unique indexes and `CHECK`s. The
  application validates too, but the database is the last line.
- **Indexes follow access patterns.** Every list query has an index matching its `WHERE` +
  `ORDER BY`. Check with `EXPLAIN ANALYZE` on realistic data, not on 10 rows.
- **Transactions** wrap each use case that writes more than one row; keep them short and never
  hold one open across a network call.
- **Seed data** gives the demo account (`test@test.com` / `testtest`) and enough users, posts
  and follows for the frontend to look alive. It runs with one command and is idempotent.
- **Soft vs hard delete:** decide per entity and write it down. Posts are a good candidate for
  soft delete, because shares point at them.

**Done:** a fresh clone gets a running, seeded database with one command.

## 5. Events and background work

- **Transactional outbox:** a write that must emit an event inserts an outbox row in the same
  transaction. A relay publishes it and marks it sent, so an event exists if and only if the
  write committed.
- **At-least-once delivery, idempotent consumers:** every consumer records processed event ids
  (or uses natural idempotency, such as upserts), so redelivery is harmless.
- **Event envelope:** `{ id (ULID), type, occurredAt, version, producer, traceparent, data }`.
  Version the payload. Add fields freely; never change the meaning of an existing one.
- **Jobs:** retries with exponential backoff and jitter, a maximum attempt count, and a
  dead-letter queue (or failed set) that you inspect. Workers are safe to kill mid-job.
- **Scheduled jobs** (trending refresh, upload cleanup) have one owner, and run idempotently in
  case of overlap.

**Done:** kill the relay or a worker mid-stream, restart it, and prove nothing is lost or
duplicated.

## 6. Security

Work through the [OWASP API Security Top 10](https://owasp.org/API-Security/). In practice:

| Area | Rule |
|---|---|
| Passwords | Argon2id with library defaults or stronger; never logged; a generic "email or password is incorrect" on failure |
| Access tokens | JWT, 15 min, asymmetric (EdDSA or RS256) so gateways can verify without the private key; validate `iss`, `aud`, `exp`, `alg` |
| Refresh tokens | Opaque, stored hashed, single use, rotated, grouped in families; reuse revokes the family (ADR-0003) |
| Object-level authorization | Every handler checks the caller may act on *this* object (owner, member, not blocked). This is the #1 API vulnerability |
| Visibility | Every read path applies post visibility and blocks, including search, feed, notifications and likes lists |
| Input | Validate size limits (body, text, arrays, `limit`). Reject unknown fields where the contract says so |
| Uploads | Never trust the client's content type; sniff magic bytes; enforce size while streaming |
| Brute force | Rate-limit `login`, `register` and `refreshTokens` per IP and per account |
| Headers | `X-Content-Type-Options: nosniff`, no `X-Powered-By`, HSTS behind TLS |
| Dependencies | Lockfiles committed; automated dependency updates and audit in CI |
| Secrets | Never in the repo; `.env` uncommitted; separate secrets per environment |

**Done:** a test suite of "user A tries to touch user B's thing" cases, all returning `404`
(can't see it) or `403` (can see it, can't change it).

## 7. Observability

- **Logs:** structured JSON, one line per event, with `level`, `msg`, `traceId`, `spanId`,
  `userId` when known, `route`, `status`, `durationMs`. No secrets or tokens; redact
  `Authorization`.
- **Traces:** OpenTelemetry. Accept and propagate W3C `traceparent` over HTTP, gRPC and event
  envelopes. Return `traceId` in problem responses so a user-visible error leads to its trace.
- **Metrics:** RED per route (rate, errors, duration as a histogram), plus queue depth, job
  age, outbox lag, database pool usage and WebSocket connections.
- **Health:** the contract's `GET /v1/health` reports identity and status. Internally, also
  expose `/livez` (process up) and `/readyz` (dependencies reachable), which the gateway does
  not route publicly.
- **Dashboards:** one per backend in Grafana with the RED metrics and the three or four signals
  that matter most for it (feed latency, outbox lag, socket count).

**Done:** pick any failed request in the frontend, copy its `traceId`, and find the full
trace and logs within a minute.

## 8. Reliability

- **Graceful shutdown:** on `SIGTERM`, fail `/readyz`, stop accepting connections, finish
  in-flight requests and jobs (with a deadline), close sockets with a reconnect hint, then
  close pools.
- **Timeouts everywhere:** on outgoing HTTP, gRPC, database and Redis calls. No unbounded
  waits.
- **Retries** only for idempotent operations, with backoff and jitter, and within a total
  deadline.
- **Circuit breakers** on calls to other services (microservices).
- **Backpressure:** bounded queues, bounded concurrency, and a `limit` cap on every list.
- **Degrade, don't fail:** if search is down the feed still works; if notifications are slow,
  likes still succeed.

**Done:** restart any one dependency during a k6 run and watch errors stay bounded and
recover.

## 9. Testing

| Layer | What | Tools (per language) |
|---|---|---|
| Unit | Domain rules: visibility, aggregation, token rotation, cursor encoding | Vitest · `go test` · `cargo test` · pytest |
| Integration | Repositories and queries against real Postgres, Mongo and Redis in containers | Testcontainers (all four languages) |
| HTTP | Each operation through the real router: status, body shape, auth | Supertest · `httptest` · `axum-test` · `httpx` |
| Contract | The whole API against `api/openapi.yaml` | `pnpm test:contract` (Schemathesis) |
| Load | Feed reads, fan-out, chat delivery, uploads | k6 |
| Chaos (later) | Kill containers mid-run | `docker kill`, Toxiproxy |

Rules: no mocking the database in integration tests; each test sets up its own data; tests
run in parallel and in any order; a failing test names the rule it protects.

**Done:** one `test` task (`pnpm test`, `make test` or the language equivalent) runs unit,
integration and HTTP tests locally and in CI.

## 10. Local development and delivery

- **One command up:** `docker compose up` starts every dependency; another starts the app with
  hot reload. Each backend names its common tasks the same way (`up`, `dev`, `migrate`,
  `seed`, `test`, `lint`, `load`). A single-language TypeScript backend keeps them as
  `package.json` scripts. A backend with several languages adds a `Makefile` (or `justfile`)
  at its root so every service answers to the same commands.
- **Containers:** multi-stage Dockerfiles, a non-root user, a pinned base image, a
  healthcheck, and only the build output in the final image.
- **CI per backend:** lint, typecheck or compile, unit and integration tests, image build, and
  contract tests against the composed stack. Path filters so a change to one backend doesn't
  rebuild the others.
- **Gateway:** nginx in front of every backend, providing TLS termination (optional locally),
  routing, per-IP rate limits (`limit_req`), a body size cap, upstream timeouts, and request
  ids. Its config is hand-written practice too.

**Done:** a new machine goes from clone to a seeded, running backend behind its gateway with
three commands, documented in the backend's README.

## 11. Documentation

- A README per backend: what it is, how to run it, how to test it, where the dashboards are.
- An ADR in `docs/adr/` for every decision that would surprise a newcomer: choosing a
  library, a data store, a consistency trade-off.
- A runbook entry for each alert: what it means, how to check, how to fix.
